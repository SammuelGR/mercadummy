# DummyJSON Data Extraction

**Only categories and products** will be extracted. Users, orders, carts and other resources are left out; user and order data will be created later.

The structure below was checked against the files and code of the [official repository](https://github.com/Ovi/DummyJSON), not against calls to the published API. That copy has 24 categories and 194 products.

The migration is done by an **external script**, `backend/src/scripts/import-dummyjson.ts`. It reads DummyJSON and sends the data to the application through HTTP, without writing directly to the database, and imports nothing from the application code.

## Sources

| Order | Request | Response | Target |
|---|---|---|---|
| 1 | `GET https://dummyjson.com/products/categories` | list of categories | `categories` |
| 2 | `GET https://dummyjson.com/products?limit=0` | object `{ products, total, skip, limit }` with all products | `products` |

Without `limit=0`, the API returns only 30 products. Check that the number of items in `products` equals `total`. The `total`, `skip` and `limit` fields are not stored.

## Categories → `categories`

| Parameter | Target | Handling |
|---|---|---|
| `slug` | `categories.slug` | direct copy |
| `name` | `categories.name` | direct copy, e.g. `Mens Shirts` |
| `url` | not stored | points to the DummyJSON API |
| (does not exist) | `categories.id` | UUID v4 generated by the system |

## Products → `products` columns

| Parameter | Column | Type | Handling |
|---|---|---|---|
| `id` | `external_id` | `integer` | keeps the source id |
| `category` | `category_id` | `uuid` | holds the slug; use the UUID of the category with that `slug` |
| `title` | `title` | `varchar(150)` | direct copy |
| `price` | `price` | `numeric(10,2)` | direct copy, price without discount applied |
| `discountPercentage` | `discount_percentage` | `numeric(5,2)` | exact copy, not rounded to an integer |
| `stock` | `stock` | `integer` | direct copy |
| `thumbnail` | `thumbnail` | `text` | stores the URL; the image is not downloaded |

## Products → `products.details`

Keys keep the same name and structure.

| Parameter | Path in `details` | Format | Note |
|---|---|---|---|
| `description` | `description` | text | |
| `rating` | `rating` | number | rating provided by DummyJSON; not recalculated |
| `brand` | `brand` | text | missing in 92 products; omit the key instead of storing `null` |
| `sku` | `sku` | text | validate that it is not repeated |
| `weight` | `weight` | number | the unit is not given |
| `dimensions.width` | `dimensions.width` | number | the unit is not given |
| `dimensions.height` | `dimensions.height` | number | |
| `dimensions.depth` | `dimensions.depth` | number | |
| `warrantyInformation` | `warrantyInformation` | text | |
| `tags[]` | `tags` | list of texts | |
| `images[]` | `images` | list of URLs | keep the order; 1 to 6 per product |

## Parameters not stored

The script discards these parameters before sending. The API rejects unexpected fields, so they cannot be passed through in `details`.

| Parameter | Reason |
|---|---|
| `shippingInformation`, `returnPolicy` | shipping and return information is not used in the project |
| `minimumOrderQuantity` | there is no minimum purchase quantity rule |
| `reviews` | the project does not display reviews; `rating` is kept |
| `meta` (`barcode`, `qrCode`, `createdAt`, `updatedAt`) | barcode and QR code are not used; dates are the application's own |
| `availabilityStatus` | would become outdated after sales; it is computed from `stock` |

## System-filled columns

In `products`:

| Column | Value on creation |
|---|---|
| `id` | UUID v4 |
| `created_at`, `updated_at` | creation time in the application |
| `is_active` | `true` |
| `version` | `1` |

In `categories`, `id`, `updated_at` and `version` follow the same rules.

## Transformation example (product 1, abridged)

Input:

```json
{
  "id": 1,
  "title": "Essence Mascara Lash Princess",
  "category": "beauty",
  "price": 9.99,
  "discountPercentage": 10.48,
  "stock": 99,
  "rating": 2.56,
  "brand": "Essence",
  "availabilityStatus": "In Stock",
  "meta": {
    "barcode": "5784719087687",
    "qrCode": "https://cdn.dummyjson.com/public/qr-code.png"
  },
  "thumbnail": "https://cdn.dummyjson.com/product-images/beauty/essence-mascara-lash-princess/thumbnail.webp"
}
```

Columns:

| Column | Value |
|---|---|
| `external_id` | `1` |
| `category_id` | UUID of the category with `slug = 'beauty'` |
| `title` | `Essence Mascara Lash Princess` |
| `price` | `9.99` |
| `discount_percentage` | `10.48` |
| `stock` | `99` |
| `thumbnail` | URL from the input |

`details`:

```json
{
  "rating": 2.56,
  "brand": "Essence"
}
```

`meta` and `availabilityStatus` were discarded.

## Running the migration

The API and, for the catalog to appear, the worker must be running. In `backend/`:

```sh
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='a-secure-password' npm run admin:create   # once
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='a-secure-password' npm run catalog:import
```

| Variable | Use |
|---|---|
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Admin account created by `admin:create` and used by the import to log in |
| `ADMIN_FULL_NAME` | Name of the admin account; defaults to `Administrator` |
| `CATALOG_API_URL` | API base URL; defaults to `http://localhost:3000` |
| `DUMMYJSON_URL` | Source base URL; defaults to `https://dummyjson.com` |

The variables can also come from `backend/.env`. `admin:create` validates the input with the same rules as registration and fails, without changing anything, if the e-mail is already registered.

The scripts compile to `dist-scripts/` with `tsc`, so they do not interfere with the `dist/` used by `start:dev`. The import exits with code `1` if the source is invalid, the login fails, the API stops responding or any record is rejected.

## Migration flow

1. The script fetches both sources and validates the data before sending anything.
2. It logs in as `admin`, sends the categories to the API and keeps the UUID of each `slug`.
3. It transforms each product and sends it to the API with the category UUID.
4. At the end, it reports how many records were created, skipped and rejected.

### Validations in the script

- `id`, `title`, `category`, `price`, `stock` and `thumbnail` are present.
- Every product `category` exists in the category list.
- `price` and `stock` are non-negative; `discountPercentage` is between 0 and 100. If `discountPercentage` is missing, stop the migration instead of assuming 0.
- `id` and `sku` are not repeated.

## What the API must support

Endpoints, request formats and errors are in `06-api-contract.md`.

- Create a category with `slug` and `name`, and return its UUID, including when the `slug` already exists.
- Create a product receiving the source id (`externalId`, stored in `external_id`) and `details`.
- Restrict these operations to an `admin`.
- Generate ids and dates in the application, without receiving them from the script.
- Write the `CategoryUpserted` or `ProductUpserted` event in the same transaction as the record, so MongoDB is updated.

### Running the migration again

A category whose `slug` already exists and a product whose `external_id` already exists are **neither created nor changed**. The API must report that the record already exists, so the script counts it as skipped and moves on. This way, stock already sold does not go back to its original value.

Each record is stored separately. If the run stops midway, what was created remains, and a new run creates the rest.
